# Spec 工作流

## 进入与阶段

- 新需求和 bug 默认先核查并输出 spec，不提前修改业务代码；可以进行只读调查和必要的基线检查。
- 已有 spec 时先读取并核对当前代码，维护同一份文档，避免每轮讨论生成新文件。
- 用户确认方案并要求开发后，按 spec 实施；已有明确实施授权时不重复请求确认。用户明确说“本次直接改”时遵从其指令，不强制补文档。
- 规划、实施、review 分清当前阶段。文档中不得把建议、假设或未执行的验证写成已确认事实。

## 文档位置：先解析，再写入

按以下优先级确定输出位置：

1. 当前用户明确指定的文件或目录。
2. 当前会话已确认的输出目录及项目映射。
3. 本机配置：`$CODEX_HOME/spec-workflow.json`；未设置 CODEX_HOME 时使用 `~/.codex/spec-workflow.json`。

配置格式见 [config.example.json](references/config.example.json)。`specRoot` 为默认根目录；`projectFolders` 将项目名映射到根目录下的相对目录。项目归属结合会话、仓库名称和代码内容识别，有歧义才询问。

- 默认只能在已配置根目录内写 spec。解析绝对路径后验证目标仍在根目录内，拒绝项目映射中的绝对路径或越界路径。
- 用户明确指定本次其他位置时遵从该位置；这不自动改写持久配置。用户明确要求修改默认生成位置、迁移输出目录或“以后都放这里”时，更新上述本机配置的 `specRoot`。
- 修改默认目录前核对新路径；保留 `projectFolders` 等未要求修改的配置，重新检查项目映射解析后仍在新根目录内。后续生成和查找已有 spec 使用更新后的目录；迁移已有文档需另有用户要求。本机绝对路径只保存在本机配置中，不硬编码进 skill 或公开仓库。
- 没有输出位置时，询问用户“spec 保存在哪个目录，是否作为默认目录？”。可以继续独立的只读调查，文档内容先在聊天展示，不创建文件。
- **不得把工作目录、仓库根目录、docs/ 或 specs/ 作为兜底目录。** 只有用户明确要求放进项目时才允许。
- 配置不存在或不完整时不擅自补默认路径；配置文件使用 JSON，不复制到公开 skill 中。
- 默认文件名为 `YYYY-MM-DD-主题-spec.md`。已有同需求文档则更新；同名但归属不同则另取名，不覆盖。

## 核查与范围

- 遵循适用的项目约定，先检查工作区，保护用户未提交的变更。
- 只读定位入口、相关实现、调用方与现有测试，先确认文案和数据来源、行为边界及实际影响面。
- 将用户要求、代码事实、建议方案和待确认项分开写；用简短依据支持重要判断。
- 将需求拆成可验收条目，给稳定编号；关联问题可共用 spec，独立问题保留独立验收项。
- 对影响行为或兼容性的歧义及时确认；内部实现细节可提出合理方案，并标为设计选择。

## SDD 与契约

生成或修订文档时读取 [spec-template.md](references/spec-template.md)，按复杂度裁剪，避免空章节和重复说明。

- 明确当前行为、目标行为、范围、排除项和完成条件。
- 为需求关联契约和验收编号，让实施者能追踪“要求—约束—验证”。
- 契约覆盖适用的可观察行为：展示、交互、状态转换、数据完整性、权限、错误和兼容性。接口需求再补请求、响应、字段、状态码及幂等等具体约定，不为纯 UI 需求虚构 API 变更。
- 明确输入、输出、空值及必要边界；仅列与本次变更有关的不变量。
- 代码位置和修改方向帮助执行，但未证实的文件位置、命令和数值要标明待核查或建议，不写成用户硬性要求。
- 存在影响正确性的未决问题时标明实施阻塞项；不以猜测填充关键业务约定。

## 按风险制定验证约定

规划阶段以只读核查为主，只有需要确认现状或可执行性时才运行针对性检查；不为填写 spec 默认启动测试、类型检查或全量基线。未运行的命令标“计划执行”。

- 每份 spec 写清风险及依据、必跑项、扩大检查的触发条件、本次不要求的检查及理由、环境依赖和停止条件。小需求可合并成一段，不强制增加多张表。
- 按可观察行为、调用方和失败后果判断风险，不按代码行数或验收条目数决定测试量。下表是默认选择；用户要求及适用项目约定优先，不擅自降低已有必需检查。

| 影响范围 | 默认验证方式 | 扩大检查的典型条件 |
| --- | --- | --- |
| 文案、局部样式、简单展示 | 相关页面或视觉验收，复用适用的已有检查 | 涉及交互、响应式布局、共享组件或构建逻辑 |
| 局部业务逻辑、一般 bug | 能表达目标行为的测试及直接受影响测试；类型检查按影响选择 | 涉及调用方、公共类型、接口或共享逻辑 |
| 权限、持久化数据、事务、并发、公共基础能力 | 相关行为测试及能证明关键约束的集成验证 | 跨模块影响、迁移、依赖或配置变化，或影响范围无法可靠界定 |

- 验收条目与测试无需一一对应；多个条目可以由同一组测试或一次页面验收覆盖。保留必要边界，避免重复证明相同契约。
- 全量测试、全项目类型检查和 lint 均需说明适用依据；项目要求、广泛影响或无法界定影响面时执行，不作为每个需求或提交前的固定流程。
- 关键契约必须有与之匹配的证据。副本集、数据库等环境未就绪时可继续独立工作，记录关键验收待验证；不能用纯函数断言替代并发、事务或持久化保证，也不能因此宣称整体验收通过。
- 接手旧 spec 缺少验证约定时，按当前影响面补充，不将历史命令清单默认解释为每一步都要执行。

## 实施中的验证与停止条件

### 选择测试与基线

- 业务 bug 和关键逻辑优先使用 TDD：复用或补充能复现问题、表达契约的测试，确认因预期原因失败，再实现并确认通过。已有测试足够时不重复新增；低风险文案、样式或配置变更按实际影响验证，不为完成 TDD 流程引入测试框架或额外重构。未确认失败时不声称完成红绿验证。
- 测试面向行为、边界和不变量，不以源码字符串匹配、函数内部步骤或仅 CSS 类名断言充数。样式、换行、省略号、响应式布局等须有真实浏览器视觉验收；缺少布局能力的 DOM 环境不能证明视觉结果。
- 修改前只建立归因或后续比较所需的相关基线；复现问题的测试结果可兼作基线，不另跑一遍。复用已有证据前核对相关代码、依赖、配置和环境，变化影响结论时才重建相关基线。没有修改前证据时如实说明，不为补记录撤销用户改动。
- 优先复用现有 fixture、stub 和测试辅助工具。纯逻辑适合独立测试时减少无关依赖；仅在确有复用或隔离收益时提取辅助函数或 fake 工厂，不把特定项目的 mock、框架或转译器方案写成通用要求。

### 控制运行范围与频率

- 迭代阶段运行能判断当前修改的最小有效检查，不要求每完成一个验收条目、每调整一次 mock 都重跑整套测试。存在新修改、失败或未解决风险时，按影响重跑或扩大范围。
- 同时考虑启动、配置加载和转译成本。昂贵检查应结合项目能力合并相关文件、复用缓存或安全并行；用例过滤、changed 模式和串行/并行参数均需核对适用性，不能假设缩小用例数就减少总耗时，或假设 changed 模式覆盖全部调用方。
- 已知依赖、配置或外部服务问题在相关条件未变化时不原样重试。意外长耗时先定位启动、转译、执行或挂起阶段，再决定下一步；不因耗时长静默取消必需验证。测试基础设施的迁移或配置优化作为独立建议，除非本次已有授权。
- 完成阶段集中补齐验证约定中的必跑项和已触发的扩大检查。针对最终相关代码及环境已通过的检查可以复用；相关条件未变化时不为“最终确认”再次运行。
- 必跑项和已触发检查已通过、没有未解决的本次风险时停止验证；不要自动追加全量测试、覆盖率或其他质量工具。无法完成必需验证时，停止无效重试，说明已完成范围、缺失证据及其对验收的影响。

### 记录证据

- 记录关键命令或验收方式、代码版本及相关工作区/环境条件、结果与必要的失败摘要；对昂贵检查记录观察到的耗时，未知耗时不编造。汇总最终有效结果，保留必要的复现失败和基线证据，不逐次堆砌重复日志。
- 区分已证实的基线问题、本次引入和归因未确定。只有相同条件下修改前的结果或其他充分证据才能证明基线；不能仅凭报错文件在修改范围外判为无关。不扩展修复无关历史问题。
- 区分通过、失败、未执行、无法执行及按约定不要求；不把计划、环境阻塞或已知失败当作通过，未解决的关键验收应保持待验证状态。

## 实施、交接和维护

- spec 应足以让未参与讨论的实施者理解目标、边界、契约、测试和停止条件，不依赖聊天补足关键决策。
- 用户另行指定模型分工时，可按“设计—实现—review”交接；skill 本身不自动创建代理、不切换模型、不假设拥有调度能力。
- 范围变化先同步 spec。关键契约不清、实现偏离契约或发现明显扩大影响面的情况，停止依赖该决策的修改并说明待决事项；其余独立工作可继续。
- 完成后更新同一份 spec 的状态及验证记录，报告实际变更、证据、基线失败和未验证项。不得仅因实施步骤完成就声称验收通过。
- 创建 spec 或完成代码不代表授权提交、推送、合并或部署；这些动作遵循用户已有授权和项目约定。
